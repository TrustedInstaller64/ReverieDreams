# 月伤 III：LTS 源码实际行为

本说明对应本分支的 0.4.10 LTS / Minecraft 1.21.8。当前修复没有改变月伤附魔的结算或强度。

后续机制提案、平衡算例与待定事项保存在 [月伤机制讨论保留稿](moon-damage-design-discussion.md)，尚未实施。

## 两种“间隔”需要分开

攻击者的攻击冷却决定这一击的蓄力与伤害；受击者的受伤保护则决定短时间内的新伤害是否被接受。1.21.8 已有受伤保护，并不是到 26.1 才出现。

Mojang 官方 1.21.8 `LivingEntity.hurtServer` 的字节码与官方映射可核对：当 `invulnerableTime > 10` 且伤害不绕过冷却时，传入伤害不超过 `lastHurt` 会被拒绝；超过时通常仅结算与上次伤害的差额。字段/方法证据来自官方 server jar，SHA-1 `6bce4ef400e4efaa63a13d5e6f6b500be969ef81`，以及同版本 server mappings；不是拿新版名称猜旧版行为。

LTS 月伤在 `Item.hurtEnemy` 后排一个延迟任务，并在任务里执行：

```java
target.hurtTime = 0;
if (target.getHealth() - itemEnchantmentLevel >= 0) {
    target.setHealth(target.getHealth() - itemEnchantmentLevel);
}
target.lastHurt = 0;
```

这里没有直接清零 `invulnerableTime`。但 `lastHurt` 被清为 0 后，保护期内后续正伤害更容易通过“是否高于上次伤害”的判定，并按伤害减 0 结算，因此会表现得像受伤间隔被绕开。`hurtTime` 主要控制受伤动画，不能把它单独解释成无敌时间。

攻击者自身的攻击冷却没有因此被移除，普通攻击仍可能因未蓄满而变弱。不过月伤的额外扣血按等级固定，并没有随攻击蓄力缩放，这又放大了快速攻击的收益。

更精确的时序是：`DelayedTask.create(server, 1, ...)` 在下一次 END_SERVER_TICK 的任务处理时执行；如果注册发生在该 tick 的末尾处理之前，可能就是当前 tick 末尾，并不保证至少经过完整 50 ms。20 TPS 下“一 tick 约 50 ms”只是时间尺度，掉 TPS 后更不能按固定墙钟时间理解。

## 是否属于“真实伤害”

对月伤 III 的额外部分，可以通俗理解为“直接扣生命值”：条件成立时减少 3 HP，即 1.5 颗心。它调用的是 `setHealth`，没有另走一次标准伤害入口，所以这一步不再经过护甲、韧性、保护附魔、抗性提升和吸收生命的标准减免/抵扣，也不受标准受伤冷却入口拦截。

边界是：

- 原来的普通攻击仍正常结算，不能把整次攻击的所有伤害都叫真实伤害。
- 必须先触发近战物品命中后的回调，读取的是攻击者主手附魔。不能推导任意伤害、任意目标都无条件触发。
- 在任务执行时，目标生命值不足 3 HP 就不执行额外扣血；恰好 3 HP 允许设为 0。因此不能称为无条件斩杀。
- 代码不要求夜晚、特定月相或月球维度。
- 直接改血会绕过通常附着于标准伤害流程的逻辑，但不能保证穿过其他模组对 `setHealth` 的拦截、锁血或特殊生命系统；也未实测其死亡归因、战利品和统计行为。

因此，你观察到的间隔异常与代码吻合；而“无视护甲、抗性”对额外补扣成立，但“无视一切机制”过于绝对。

## 与 master 的区别

当前 26.1.2 master 把月伤移入 `EnchantmentHelper.modifyDamage`：仅 overworld clock 的日内时刻 13000–23000 返回附魔等级，III 加入 3 点伤害后继续正常攻击结算。它没有 LTS 这段延迟改血与清零 `lastHurt` 的逻辑。

本轮按用户要求保留 LTS 玩法。若后续要调整月伤，应单独决定：是否取消 `hurtTime/lastHurt` 重置、保留还是替换直接扣血、是否按攻击冷却缩放、是否改变低血量边界，再做战斗回归；不应混在音乐资源修复里悄悄改变平衡。
